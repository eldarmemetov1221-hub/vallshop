# VallShop — магазин цифровых товаров

Магазин цифровых товаров поверх API поставщика **LioGames Distribution Hub**.
Старт — **PUBG Mobile UC** (ваучер-коды), затем другие игры.

> **Статус:** каркас проекта. На этом шаге реализован только чистый клиент
> LioGames + справочник API. Витрина, оплата и реальные закупки — **впереди**,
> после выбора платформы и платёжного провайдера (см. «Открытые решения»).

## Что уже есть

- [`LIOGAMES_API.md`](./LIOGAMES_API.md) — полный справочник API поставщика (источник правды).
- [`liogames/`](./liogames) — автономный Python-клиент LioGames (единственная зависимость — `requests`):
  - подпись HMAC-SHA256 от **точного** сырого JSON-тела;
  - `balance()`, `order_create()`, `order_status()`;
  - `extract_code()` — достаёт код из `sn` / `delivery_code` / `delivery.codes[]`;
  - `status_is_terminal_ok()` / `status_is_terminal_failed()`;
  - `resolve_variation_id()` — по карте из `.env` (не зависит от сломанного `/products`);
  - **mock-режим** без сети для разработки и тестов.
- [`.env.example`](./.env.example) — шаблон окружения (секреты только в `.env`, он в `.gitignore`).
- [`tests/`](./tests) — базовые тесты клиента.

## Быстрый старт

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env            # заполнить LIOG_SECRET

# Тесты (работают в mock-режиме, сеть не нужна):
pip install pytest && pytest -q
```

Пример использования:

```python
from liogames import LioGamesClient

client = LioGamesClient.from_env()          # читает .env-переменные из окружения

vid = client.resolve_variation_id(60)       # 60 UC -> 534124
data = client.order_create(vid, client_ref="shop-order-1001")
order_id = data["order_id"]

status = client.order_status(order_id=order_id)
if LioGamesClient.status_is_terminal_ok(status):
    code = LioGamesClient.extract_code(status)   # код выдачи покупателю
```

> Переменные окружения грузятся как есть; в деве можно использовать `python-dotenv`
> или `set -a; source .env; set +a` перед запуском.

## Безопасность

- Секрет подписи `LIOG_SECRET` и любые ключи — **только** через переменные
  окружения / `.env`. В репозитории — лишь `.env.example`.
- `member_code` — идентификатор, не секрет, но тоже вынесен в `.env`.
- `.env` и кэши — в `.gitignore`.

## Архитектура магазина (предложение)

Потоки и слои, вокруг которых строится магазин:

### 1. Витрина (catalog)
Наш каталог поверх вариаций LioGames: цена продажи = цена GOLD × наценка
(или фикс-прайс). Соответствие «номинал → variation_id» держим у себя
(карта в `.env`/БД), **не** полагаясь на сломанный `/products` поставщика.

### 2. Корзина / заказ
Пользователь выбирает товар и номинал → формируется заказ в нашей БД со своим
`client_ref` (идемпотентность на стороне LioGames).

### 3. Оплата (payments) — слой провайдеров
Единый интерфейс (`create_invoice` → `verify`/`webhook` → отметка «оплачено»),
за которым скрыты конкретные провайдеры (CryptoBot / Telegram Stars / ЮKassa /
своя крипта). **LioGames денег от покупателей не принимает** — это полностью
наш слой.

### 4. Выдача (fulfillment)
- **Основной путь — сток:** заранее закупаем ваучер-коды в нашу базу и выдаём
  **мгновенно** после оплаты. Это обходит лимит поставщика ~1 заказ / 60 сек.
- **Фолбэк — топап-под-заказ:** если стока нет, создаём заказ в LioGames
  (`order_create`), опрашиваем `order_status` до финала, извлекаем код
  (`extract_code`). Медленнее и упирается в лимит 60 сек.

### 5. Хранилище (storage)
БД для: заказов (+ статусы, `client_ref`, `order_id`), стока кодов (с состоянием
«свободен/зарезервирован/выдан»), пользователей, платёжных транзакций.

### 6. Статусы и вебхуки (webhooks)
- Приём вебхуков LioGames (callback URL в панели, отвечаем 2xx) как основной
  сигнал о готовности заказа.
- Фолбэк — поллинг `order_status` до финального статуса.
- Приём вебхуков платёжных провайдеров для подтверждения оплаты.

### Эксплуатационные ограничения
- Кошелёк поставщика пополняется **вручную** (USDT BEP-20), API нет — нужен
  мониторинг баланса (`balance()`) и алерты, чтобы сток/фолбэк не встали.
- Лимит заказов делает **сток основным механизмом**, а топап — аварийным.

## Открытые решения (нужен выбор пользователя)

Перед реализацией витрины и оплаты нужно определиться с двумя пунктами:

1. **Платформа:** Telegram-бот **или** веб-сайт (или оба). От этого зависит
   слой `app/` и UX.
2. **Платёжный провайдер:** CryptoBot / Telegram Stars / ЮKassa / своя крипта
   (можно несколько). От этого зависит, какие реализации в `payments/` писать
   первыми.

До этого выбора оплата и витрина **не реализуются** и реальные закупки **не
делаются**.
